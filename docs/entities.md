# Entities

[README](../README.md) > Entities

Each monitor becomes a device named **Radon &lt;label&gt;** (manufacturer *Ecosense (FTLab)*, model
*RD200*) with the entities below. Two more entities belong to the integration as a whole.

Entity IDs are generated by Home Assistant from the device name and the entity name, when the entity is first
created. All examples use the label `upstairs`; yours follow your label. Renaming an entity ID in the UI is
safe (the [migration guide](migration-from-rd200_ble.md) relies on it).

| Entity | Entity ID | Unit | Device class | State class | Updates |

| RadonEye log last pull | `sensor.radoneye_log_last_pull` | (timestamp) | timestamp | none | after each daily or requested pull |

The radon device class is used where your Home Assistant version provides one (the code falls back to no
device class otherwise). It is the same one `rd200_ble` uses, which is what lets this integration's sensors
continue `rd200_ble`'s long-term statistics (see [Migration](migration-from-rd200_ble.md)). The entities
are refreshed every minute internally, but Home Assistant records a new state only when the value or an
attribute changes, so the "Updates" column is what you will see in history.

## Availability rules

| Entities | `unavailable` when | `unknown` when |
|---|---|---|
| Radon, 1-day level, 1-month level, peak (the **device values**) | No good read for **20 minutes**, and after a Home Assistant restart until the first good read. A stale device value is never shown as current. | 1-day, 1-month and peak only: the monitor restarted less than **60 minutes** ago (it reports 0 for these then). |
| Radon (counts, 1 h) | Fewer than **4 of the last 6** windows captured, or the monitor is not in counts mode. | - |
| Radon (counts, 24 h) | Fewer than **120 of the last 144** windows captured, or not in counts mode. | - |
| All others | never (they always report) | No data yet (for example no completed 4 h block, or no backup reader check yet). |

The 20-minute rule applies only to the device values. Counts-based values follow their coverage rule, and
reliability and diagnostic entities keep reporting, so you can see *why* the device values went away.

If a monitor has not been read for **1 hour**, a persistent notification *Radon &lt;label&gt; has not been
read since ...* appears; it is dismissed automatically at the next good read.

## Device values

**Radon**, **Radon 1-day level**, **Radon 1-month level** and **Radon peak** are exactly what the monitor
reports: its latest value, its own 1-day and 1-month averages, and its peak, converted from the device's
Bq/m³ integers to pCi/L with 2 decimals. They are read at every good read, so they change about every
5 minutes in counts mode.

**Last boot** is the time the monitor last powered up, computed from its uptime and rounded to the minute. It
changes only when the monitor restarts (a restart is also written to the logbook: *Radon upstairs restarted
(uptime 3 min)*). After a restart the monitor's window numbering starts again and its averages are unknown
for an hour.

## Counts-based radon

**Radon (counts, 1 h)** and **Radon (counts, 24 h)** are computed from the archived particle counts:

```text
radon (Bq/m³) = (N / T) / k        radon (pCi/L) = radon (Bq/m³) / 37
```

where N is the total count in the windows **captured** in the period and T their total duration in hours.
Missing windows shorten T; they never count as zero. The method is described in detail in
[the counts method](technical/counts-method.md).

| Attribute | Example | Meaning |
|---|---|---|
| `lower` | `0.69` | Lower end of the 68 % interval, pCi/L (exact Poisson, Garwood) |
| `upper` | `0.742` | Upper end of the 68 % interval, pCi/L |
| `coverage` | `0.986` | Captured windows / expected windows (6 or 144) |
| `factor` | `1.27` | The *k* used, counts per hour per Bq/m³ |

The state is rounded to 4 decimals and displayed with 2; `lower` and `upper` are rounded to 3 decimals.
`coverage` and `factor` are not stored in the recorder's state history (they would only bloat it);
`lower` and `upper` are.

At typical indoor levels a 10-minute window holds only a few counts (about 2 at 10 Bq/m³), so the 1 h value
moves a lot from hour to hour and its interval is wide. That is honest, not a fault. The 24 h value is the
one to trend. Example from a real monitor: 24 h value 0.7156 pCi/L, `lower` 0.69, `upper` 0.742, while the
device's own 1-day level showed 0.65.

Only the 1 h value has a state class, so only it gets long-term statistics. The 24 h value would only
duplicate them; the [hourly counts statistics](#hourly-counts-statistics) cover long periods exactly.

## Reliability and diagnostics

These are explained fully in [Reliability](reliability.md).

**First-attempt read success (4 h)**: the share of scheduled reads (A and B, with a daily pull counting as A)
whose **first** attempt succeeded, in the **previous** fixed 4-hour block of local time. Attribute:

| Attribute | Example | Meaning |
|---|---|---|
| `block_start` | `2026-10-05T16:00:00-05:00` | Start of the block the value describes (local time) |

The value is `unknown` until the first block containing scheduled reads has finished, and for a block during
which Home Assistant was not running. It only counts in counts mode (in device-values-only mode there are no
scheduled A/B reads).

### Diagnostics

- **Window capture (24 h)**: captured / (captured + missed) for windows that ended in the last 24 hours.
  Windows that closed while Home Assistant was not running are *not observed* and excluded.
- **Missed windows (24 h)**: the number of windows in the last 24 hours that every read failed to capture
  and that no backup supplied.
- **Counts vs device (7 d)**: counts-based radon divided by the device's own latest value, over the last
  7 days of windows (needs at least 144 windows, otherwise `unknown`). Close to 1 means *k* and the device
  agree; see the [FAQ](faq.md#calibration-and-the-factor-k).
- **Signal strength** (disabled by default): the RSSI in dBm of the monitor's advertisement as last heard by
  Home Assistant's Bluetooth, taken at each read. Enable it under the device page if you are working on
  placement.
- **Last good read** (disabled by default): the time of the last successful read.
- **Backup reader reachable**: on if the backup reader answered the last request, off if it did not;
  `unknown` until the first check after a start or reload (within the first minute).

## Integration-wide entities

**RadonEye log last pull**: the time the most recent daily (or requested) log pull finished, kept across
restarts. Attributes:

| Attribute | Example | Meaning |
|---|---|---|
| `all_ok` | `true` | Every monitor's last pull succeeded |
| `radon_<label>` | `radon_upstairs: ok` | `ok` or `failed`, per monitor |
| `radon_<label>_detail` | `{ok: true, points: 8760, filled_hours: 2, uptime_minutes: ..., latest_pci_l: ..., firmware: ..., read_at: ..., finished: ...}` | Details, or `{ok: false, error: ...}` |

**RadonEye radio time share**: the percentage of the last hour that this integration spent connected to
monitors (including `rd200_ble` refreshes in a parallel run). Above 50 % a notification asks you to add a
Bluetooth proxy. See [Reliability](reliability.md#radio-time-share).

## What is kept in long-term statistics

| Kept (state class *measurement*) | Not kept |
|---|---|
| Radon, Radon 1-day level, Radon 1-month level, Radon peak | Radon (counts, 24 h) |
| Radon (counts, 1 h) | Window capture, Missed windows, Counts vs device |
| First-attempt read success (4 h) | Signal strength, Last good read, Last boot |
| | Radio time share, Last pull, Backup reader reachable |

In addition, each monitor writes two **external statistics** (below). Diagnostics have short-term state
history only (the recorder's normal retention, 10 days by default).

## Hourly counts statistics

For every monitor the integration keeps two hourly statistics, written directly into Home Assistant's
long-term statistics:

| Statistic ID | Name | Unit | Hourly value |
|---|---|---|---|
| `reliable_radoneye:counts_<serial>` | *Radon &lt;label&gt; counts per hour* | counts | Total particle count of the windows that **ended** in that clock hour |
| `reliable_radoneye:windows_<serial>` | *Radon &lt;label&gt; windows per hour* | windows | Number of windows captured that ended in that hour (6 when complete) |

`<serial>` is the serial in **lower case**, for example `reliable_radoneye:counts_xx01re000001`. Each hour's
mean, min and max are all the same exact number. An hour is rewritten whenever a window ending in it is
added, so a window filled in later by the backup reader updates its hour.

These statistics are the exact long-term record: they keep the raw counts, independent of *k*. From them you
can work out radon for any hour or longer period:

```text
radon (pCi/L) = (counts / windows × 6) / k / 37
```

With all 6 windows captured this is simply `counts / (k × 37)`; with k = 1.27, `counts / 47`.

### Chart them with the statistics graph card

The built-in **Statistics graph** card accepts external statistic IDs:

```yaml
type: statistics-graph
title: Radon upstairs - counts per hour
entities:
  - entity: reliable_radoneye:counts_xx01re000001
    name: Counts per hour
period: hour
stat_types:
  - mean
chart_type: bar
days_to_show: 7
```

Daily view (the mean of the hourly values, that is the average counts per hour that day):

```yaml
type: statistics-graph
title: Radon upstairs - average counts per hour, by day
entities:
  - reliable_radoneye:counts_xx01re000001
  - reliable_radoneye:windows_xx01re000001
period: day
stat_types:
  - mean
days_to_show: 90
```

A drop in the windows line (below 6) shows hours that were not fully captured, so you can tell a real dip in
counts from missing data.

### Chart them as radon with apexcharts-card

The community [apexcharts-card](https://github.com/RomRider/apexcharts-card) can read long-term statistics
and transform them. This converts counts per hour to pCi/L, assuming complete hours and k = 1.27:

```yaml
type: custom:apexcharts-card
header:
  show: true
  title: Radon upstairs from counts (hourly)
graph_span: 7d
series:
  - entity: reliable_radoneye:counts_xx01re000001
    name: Radon (counts)
    unit: pCi/L
    statistics:
      type: mean
      period: hour
    transform: "return x / (1.27 * 37);"
    float_precision: 2
```

Not verified here: whether your apexcharts-card version accepts an external statistic ID (with a colon) in
`entity`. If it does not, use the statistics graph card above, or plot the Radon (counts, 1 h) sensor's own
statistics instead.
